# 实施与验收

## 1. 发现真实入口

记录 AppID/OfferID/环境对应关系，普通支付创单、客户端调起、通知、主动查单、会员与课程发货、退款/对账、登录态入口。保存脱敏基线和部署文件哈希。历史普通订单继续由原通道处理，不将它们强行改标为虚拟订单。

检查源代码与编译输出是否使用同一配置。预览码记录版本、构建时间、哈希、试点账号及失效时间，避免把旧预览结果归因于新代码。

## 2. 商品契约

逐项建立：业务套餐ID、有效售价、微信商品ID、数量、期限、权益、适用业务范围、上下架状态。价格变化需同步映射，不从显示名称猜商品。区分会员、课程、组合包及未开放商品。校验所有可买套餐，不能只测一个套餐。

## 3. 服务端与会话

复用原账号身份，明确微信 openid 属于哪个 AppID、登录 session_key 的来源与更新。支付门控与登录校验错误分开记录。若采用 stable_token，按当前文档普通模式获取并缓存，通常不强制刷新；不同 token 获取方式的隔离关系须核实，避免干扰旧业务。

业务购买意图、支付尝试、可信支付事件、权益发放记录分别持久化。建议的唯一约束：支付尝试号、平台交易标识、业务意图发货标识；具体索引取决于业务，不直接复制旧项目表结构。

回调先验签/解密，绑定可信订单、账号、商品及官方提供的金额/环境等证据。缺失字段不得从请求反填后冒充平台证明。事务内锁定、检查、发权益、记账；失败可重试，成功响应与内部持久化结果一致。外部发货用 outbox 或等效幂等恢复机制。

## 4. pending 与重付

伪流程（状态值按当前官方契约映射，不能硬编码案例数字）：

```
点击购买 -> 服务器校验身份/商品/价格，锁定购买意图
  有旧尝试 -> query_order
    已支付 -> 校验支付证据 -> 幂等发货 -> 返回完成
    明确未支付且超时 -> 标记本地不可续付 -> 新支付尝试
    明确关闭/取消 -> 按契约允许新支付尝试
    查询未知 -> 返回具体阶段与错误，不伪造关闭或已支付
    明确未支付且未超时 -> 按选定策略等待，或核对后本地停止旧尝试
  无阻塞尝试 -> 生成全新outTradeNo -> 签名 -> 拉起收银台
```

新旧尝试均纳入补偿查单。若停止旧单续付后旧单到账：同一意图尚未发货则发一次；已经发货则记录额外到账，启动对账退款/人工处理，不吞钱、不重复发权益。独立续费意图按正常规则续期。

## 5. 最小部署

独立配置与灰度账号，先部署闭合服务端，再启客户端门控。新增表/索引先评估锁表和容量，隔离库验证事务、回滚、并发。共用服务器不改全局PHP、其他站点和数据库权限。配置/代码回滚不能删除真实到账、订单和权益历史。

## 6. 验收矩阵

- iOS与Android：微信登录/手机号登录后支付身份正确，无试点误拒绝。
- 所有开放套餐：页面价、后端价、收银台金额一致；课程与会员分别测。
- 首次打开、取消后重开、连续两次取消再开、快速双击/弱网重试。
- pending未支付超时；查询异常；平台关闭；客户端报错与服务器查询不同步。
- 旧单迟到到账、新旧分别到账、通知重放、查单与通知并发、发货事务故障重试。
- 新会员、已有会员续期、权益绑定、课程权限；真实支付由用户本人完成。
- 原普通支付历史查单/退款、其他客户端登录及付款、题库/资料/发现页面布局。

每次真机证据关联：构建ID、脱敏账号、业务意图号、outTradeNo、时间、客户端错误、后端阶段、平台原始脱敏查单、权益前后值。保存原始状态字段，不用自定义摘要代替事实。

## 7. 发布

先核对线上门控与审核账号可用性、类目及商品范围，准备审核说明。不得把预览支付成功等同正式版已生效。提交/发布后从正式入口回读版本并验证。交付代码、配置、回滚点、商品表、证据和未验收项目。
